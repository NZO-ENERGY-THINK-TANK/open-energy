## T05 — Centralize API access and secure the development proxy

- Status: TODO
- Depends on: T01 approvals, T02, T04; use T03 test tooling.
- Objective: Provide browser-safe relative requests to existing Python contracts through a narrowly scoped development proxy.
- References: E01 request matrix, `apps/frontend/vite.config.ts`, `apps/frontend/config`, shared request code, read-only legacy proxy/API code and Python route/authentication contracts.
- Allowed writes: frontend Vite/proxy configuration, public request allowlist, shared API utilities under `apps/frontend/src/lib`, focused proxy/API tests, and an ignored-variable template without secrets.
- Forbidden writes: Python/reference source, feature page implementations, production proxies, authentication redesign.

### Work

- Keep browser requests relative. Separate Node-only upstream/key configuration from browser-safe API helpers.
- Preserve existing parameter serialization, response/error handling, and download behavior required by retained consumers; do not add speculative client abstractions.
- Require an explicit path-and-method allowlist for key-bearing data requests. Keep contact/survey POST forwarding separate and do not attach the legacy key to those public form requests.
- Strip caller credentials before upstream forwarding. Never forward the key to an unapproved origin, including through redirects.
- Implement approved endpoint/slash compatibility using canonical paths or safe same-origin handling; do not silently convert all redirects into successful responses.
- Document `UPSTREAM_ORIGIN`, `OPEN_ENERGY_API_KEY`, and backend `INTERNAL_API_KEY` precedence as actually implemented. Keep local development loopback-only by default.
- Fail clearly for missing key, invalid configuration, unavailable upstream, and disallowed requests without exposing secrets.
- Keep `vite preview` free of the key-bearing development proxy. Do not implement production API access.

### Acceptance and validation

- `pnpm --filter frontend test` covers allowed requests, rejected administrative paths/methods, encoded path variants, credential stripping, configuration failures, and approved slash/forecast cases.
- Use a local mock upstream to verify forwarded path/query/body, download headers/body, upstream failures, and redirect/key containment. Do not call Google or administrative backend operations.
- Verify the browser client and production output contain no test credential; use a dummy credential, never a real secret, for this check.
- Report backend connectivity separately if unavailable. A mocked contract check is not a successful live backend check.

- API/proxy files changed: pending
- Mock cases and exact results: pending
